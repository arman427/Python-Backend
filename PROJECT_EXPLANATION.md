# Объяснение архитектуры проекта

## Что делает backend

Сервис хранит пользователей, группы, студентов, занятия, посещаемость, оценки и QR-сессии. Он проверяет права пользователей и бизнес-правила, читает и изменяет PostgreSQL и возвращает frontend JSON через REST API.

Общий путь запроса:

```text
Frontend → API router → dependency → service → repository → SQLAlchemy → PostgreSQL
                                              ↓
Frontend ← JSON/Pydantic schema ← результат бизнес-логики
```

## Структура

### `app/main.py`

Точка входа. Здесь создаётся объект `FastAPI`, подключается CORS, обработчик ошибок и все router с общим префиксом `/api/v1`.

`/api` показывает, что URL относится к программному API. `/v1` фиксирует первую версию контракта: в будущем несовместимые изменения можно выпустить как `/api/v2`, не ломая старый frontend.

### `app/api/`

Транспортный слой. Router принимает HTTP-запрос, извлекает path/query/body, запускает зависимости и передаёт данные сервису. В router не должна находиться сложная бизнес-логика.

Пример:

```python
@router.post(
    "/lessons/{lesson_id}/grades",
    response_model=GradeResponse,
    status_code=201,
    summary="Выставить оценку",
)
async def create_grade(...):
    return await service.create_grade(...)
```

Значение элементов:

- `@router.post(...)` регистрирует функцию как обработчик HTTP POST;
- `"/lessons/{lesson_id}/grades"` задаёт маршрут, а `{lesson_id}` становится path-параметром;
- `response_model` проверяет и документирует структуру ответа;
- `status_code=201` означает, что создан новый объект;
- `summary` и `description` отображаются в Swagger;
- `Depends(...)` просит FastAPI получить зависимость: БД, текущего пользователя или service;
- `Annotated` одновременно хранит Python-тип и описание зависимости для FastAPI.

Файлы:

- `auth.py` — регистрация, login, refresh и профиль;
- `teacher.py` — занятия и студенты группы;
- `swipe.py` — ручная отметка посещаемости;
- `qr.py` — два QR-сценария;
- `grades.py` — оценки;
- `reports.py` — статистика и CSV.

### `app/api/dependencies.py`

Связывает слои. `get_db` выдаёт сессию БД, `get_current_user` декодирует Bearer JWT, `require_role` проверяет роль, а функции `get_*_service` собирают service из нужных repository.

Это Dependency Injection: классы не создают зависимости внутри себя, а получают их снаружи. Благодаря этому код легче тестировать и заменять mock-объектами.

### `app/services/`

Слой бизнес-логики. Он решает, разрешена ли операция.

Примеры правил:

- преподаватель может работать только со своим занятием;
- студент должен принадлежать группе занятия;
- один студент отмечается на занятии один раз;
- оценка 2–5 ставится только при `PRESENT` или `LATE`;
- динамический QR имеет ограниченный срок действия;
- студент не может подтвердить QR чужой группы.

Service вызывает repository, но не формирует SQL напрямую.

### `app/repositories/`

Слой доступа к данным. Repository выполняет запросы SQLAlchemy: `select`, `insert`, чтение по ID, сохранение и обновление.

Например, `AttendanceRepository` ищет отметку по паре `lesson_id + student_id`, получает отмеченных студентов и создаёт посещаемость. Уникальное ограничение в БД дополнительно защищает от дублей.

Разделение полезно тем, что API ничего не знает о SQL, а service не дублирует запросы к БД.

### `app/models/`

SQLAlchemy ORM-модели описывают таблицы PostgreSQL и связи:

- `UserORM` — пользователь и роль;
- `GroupORM` — учебная группа;
- `StudentsORM` — связь пользователя-студента с группой;
- `LessonORM` — занятие преподавателя для группы;
- `AttendanceORM` — статус посещаемости студента на занятии;
- `GradeORM` — оценка студента за занятие;
- `QRSessionORM` — динамический QR занятия.

Основные связи:

```text
User(TEACHER) 1 ── N Lesson
Group         1 ── N Student
Group         1 ── N Lesson
Lesson        1 ── N Attendance N ── 1 Student
Lesson        1 ── N Grade      N ── 1 Student
Lesson        1 ── N QRSession
```

Foreign Key обеспечивает ссылочную целостность. Unique Constraint не позволяет создать две отметки или две оценки одному студенту за одно занятие. Check Constraint ограничивает оценку диапазоном 2–5.

### `app/schemas/`

Pydantic-схемы описывают входной и выходной JSON. Они валидируют типы до запуска бизнес-логики и формируют документацию OpenAPI.

Например, `GradeCreate` требует целый `student_id`, оценку 2–5 и необязательный комментарий. `GradeResponse` задаёт точный формат ответа.

ORM-модель и Pydantic-схема решают разные задачи: ORM представляет строку БД, схема представляет контракт HTTP API.

### `app/core/`

- `config.py` читает `.env` через Pydantic Settings;
- `security.py` хэширует пароли Argon2, проверяет пароль и создаёт/декодирует JWT.

Пароли не хранятся открытым текстом. Access token используется для API, refresh token выпускает новую пару токенов.

### `app/db/db.py`

Создаёт асинхронный SQLAlchemy engine и `AsyncSession`. Одна HTTP-операция получает отдельную сессию через `get_db`. При исключении транзакция откатывается.

### `migrations/`

Alembic управляет версиями структуры БД. Миграция `0001_initial.py` создаёт таблицы, enum, foreign key, unique и check constraints. Команда `alembic upgrade head` приводит БД к последней версии.

### `app/seed.py`

Идемпотентно создаёт демонстрационные данные: преподавателя, администратора, 30 студентов, две группы и пять занятий. Повторный запуск не должен дублировать данные.

### Docker

`docker-compose.yml` запускает PostgreSQL и API. API ждёт healthcheck базы, применяет Alembic, запускает seed и затем Uvicorn. Внутри Docker база доступна по имени сервиса `db:5432`; с Windows-хоста — `127.0.0.1:15432`.

## Что такое OpenAPI

OpenAPI — машинно-читаемое описание API: маршруты, методы, параметры, JSON-схемы, ответы и авторизация. FastAPI генерирует его автоматически по router, типам и Pydantic-схемам.

В проекте документ доступен по `/api/v1/openapi.json`. Swagger UI по `/docs` читает этот JSON и строит интерактивную страницу. Frontend также может сгенерировать из него TypeScript-типы и API-клиент.

`openapi_extra` в login нужен из-за двух поддерживаемых форматов одного запроса:

- frontend отправляет JSON `email/password`;
- стандартная кнопка Swagger Authorize отправляет OAuth2 form `username/password`.

FastAPI не может вывести оба варианта из одной обычной сигнатуры автоматически, поэтому `openapi_extra` вручную добавляет оба `Content-Type` в OpenAPI. Это влияет на документацию запроса, а фактический разбор выполняет `parse_login`.

## Авторизация по шагам

1. Клиент вызывает `/auth/login`.
2. Service находит пользователя через `UserRepository`.
3. Argon2 проверяет пароль относительно хэша.
4. Backend возвращает access и refresh JWT.
5. Клиент отправляет `Authorization: Bearer <access_token>`.
6. `OAuth2PasswordBearer` извлекает токен.
7. `get_current_user` проверяет подпись, срок, тип токена и пользователя.
8. `require_role` разрешает или запрещает endpoint.

Коды: `401` означает проблему с авторизацией, `403` — пользователь распознан, но у него недостаточно прав.

## Короткое объяснение преподавателю

«Проект построен по слоистой архитектуре. Router отвечает за HTTP-контракт, Pydantic — за валидацию JSON, service — за бизнес-правила, repository — за запросы, SQLAlchemy models — за таблицы и связи PostgreSQL. Зависимости собираются через FastAPI Depends. Авторизация работает через JWT и роли. Структура базы версионируется Alembic. Swagger строится из OpenAPI автоматически. Docker Compose поднимает базу и API одной командой, затем применяет миграцию и добавляет тестовые данные».

## Демонстрация на защите

1. Показать `docker compose up --build` и healthcheck.
2. Открыть `/docs` и авторизоваться преподавателем.
3. Получить `/teacher/lessons`, выбрать `lesson_id=1`.
4. Получить студентов или swipe queue.
5. Отметить студента `PRESENT`.
6. Выставить ему оценку.
7. Показать summary и CSV.
8. Попробовать поставить оценку отсутствующему и показать осмысленную ошибку 400.
9. Объяснить, что БД также защищает данные constraints, даже если в прикладной логике появится ошибка.
